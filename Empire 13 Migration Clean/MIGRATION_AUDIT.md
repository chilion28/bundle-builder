# CityLocs Empire 13 migration audit

Date: 2026-08-11

## Safety boundary

- Source/reference only: production `OG-Empire` (Empire 7.0.1).
- Working copy: production draft `Empire 13 Migration Clean` (theme ID `153643909208`).
- Dev destination: `citylocsdev.myshopify.com`.
- Nothing in this migration may be pushed to or published over the production live theme.

## Current result

Shopify created a clean Empire 13.0.0 theme, but could not rebase the old edits in core files. This is the correct migration base: Empire 13's current product code remains intact, while standalone CityLocs and GemPages files were carried into the draft.

The theme contains 98 product templates. Only `product.high-variant.json` uses Empire 13's new `main-product-high-variant` section. The migrated templates still use one of these paths:

- Legacy Empire `static-product` or `static-product-3-columns` sections.
- GemPages-generated `gp-section-*` product sections.
- Bespoke Liquid templates and CityLocs product builders.

Therefore, installing Empire 13 alone does not make every assigned product template high-variant compliant.

## Empire 13 compliant reference path

The reference implementation is:

- `templates/product.high-variant.json`
- `sections/main-product-high-variant.liquid`
- `snippets/section.flex-pdp.variant-picker.liquid`
- `snippets/product.hot-reload.liquid`
- `snippets/product.hot-reload.radio-attributes.liquid`
- `snippets/product.hot-reload.select-attributes.liquid`

It uses `product.options_with_values`, option-value availability/selection metadata, `product_url`, option-value IDs, the `option_values` request parameter, and Section Rendering to replace the product UI after a selection. This is also the path required for Combined Listings sibling-product navigation.

## Migration groups

### A. Standard Empire product templates

Examples include `product.json`, `product.custom.json`, `product.description-bottom.json`, `product.fishing-hat-layout.json`, `product.pre-order.json`, and many `product.gem-*-template.json` files whose main product section is still `static-product`.

Action: rebuild the product-information portion on `main-product-high-variant`, preserving safe downstream sections such as recommendations, recently viewed products, app blocks, and informational GemPages sections. Do not copy the old `static-product` form back into the new template.

### B. Native GemPages product templates

There are multiple `product.gp-template-*` templates whose primary product UI is generated by `gp-section-*`. Those generated sections may own their own variant picker, gallery, and add-to-cart implementation.

Action: test each assigned GemPages product template independently. If its product widget serializes or loops through `product.variants`, it cannot be declared compliant merely because Empire 13 is installed. Prefer an Empire 13 high-variant product-information section plus GemPages content sections, or obtain a GemPages widget/version explicitly supporting Shopify high-variant products and Combined Listings.

### C. CityLocs custom product builders

Known full-variant dependencies:

- `snippets/cl-ai-hat-builder.liquid` builds a complete variant JSON map and searches variants for color imagery.
- `snippets/cl-pack-size.liquid` builds a price map for every variant.
- `assets/cl-ai-hat.js` consumes the full variant map emitted by the AI hat builder.
- Legacy GemPages Liquid product templates also contain full-variant assumptions.

Action: convert these builders to option-value-driven selection and server-rendered refreshes. Custom multi-line-item behavior must be retained after the selected variant is resolved.

### D. Collection pack builder

`snippets/cl-pack-grid.liquid` serializes every variant for every product in a collection. This is a collection-page scalability issue and cannot use the product-page Section Rendering flow unchanged.

Action: replace the complete inline variant payload with a lazy, per-product resolver or Storefront API/app endpoint. Treat this as a separate workstream from the product template conversion.

## Conversion order

1. Establish a clean high-variant product template and verify ordinary products and a Combined Listing.
2. Port CityLocs visual/global integrations that do not replace Empire's product form.
3. Rebuild standard product templates from the high-variant reference.
4. Convert the AI hat, customizer, upsell, and bundle product flows individually.
5. Validate GemPages product templates and replace incompatible product widgets.
6. Refactor the collection pack grid's full-variant payload.
7. Run theme checks and browser tests, then push only to an unpublished dev-store theme.

## Acceptance checks

- A product with more than 250 variants can select any valid option combination.
- Availability updates after every selection without relying on a complete `product.variants` payload.
- Combined Listing sibling selection changes the product URL and fully refreshes product-specific content.
- Price, media, SKU, inventory, quantity rules, selling plans, and add-to-cart variant ID update together.
- CityLocs personalization properties and multi-line-item cart behavior survive section refreshes.
- Back/forward navigation and direct variant/option-value URLs restore the correct state.
- No migration push targets the production live theme.
