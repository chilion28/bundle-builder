# Shopify `__ref_id` Investigation

## Executive finding

`__ref_id` is a private, order-level cart attribute that began appearing on CityLocs orders on September 1, 2026. It is not generated by the Alabama product, CityLocs bundle code, the post-purchase application, Zepto Product Personalizer, GemX, or the Product Warnings storefront extension examined in this investigation.

The strongest evidence places its creation in a server-side checkout or app/platform layer. A clean isolated browser trace found no `__ref_id` write during product-page load, add-to-cart, or checkout navigation. Shopify intentionally prevents private cart attributes—keys beginning with two underscores—from being returned through Liquid or the Ajax Cart API, while carrying them into the resulting order.^1,2

The attribute is unlikely to be an Alabama-specific production-routing problem. It occurs across unrelated hats, metal plates, and pack-builder orders. It can, however, expose a latent parsing defect in an order downloader: every observed value is a 28-character opaque string containing punctuation, and many contain CSV, URL, JSON, shell, or SQL-sensitive characters.

## Confirmed facts

### Attribute scope

The Shopify Admin screenshots and Admin GraphQL API both place `__ref_id` in the order's `customAttributes`, displayed as **Additional details**. It is not a line-item property. Line-item customization and bundle properties remain separate.

Shopify defines attributes as key-value metadata that can be attached to carts and orders, and states that cart attributes carry over to the completed order.^2 Shopify's Ajax Cart API documentation defines a key with a double-underscore prefix as a **private cart attribute**. Private cart attributes:

- are hidden at checkout;
- are visible on the Shopify Admin order page;
- are unavailable through Liquid `cart.attributes`;
- are unavailable through the Ajax Cart API.^1

This exactly matches the observed behavior.

### Onset and prevalence

A read-only Admin GraphQL audit examined the 1,000 newest orders, spanning August 30 through September 9, 2026.

The oldest sampled order containing it was **#407191**, created September 1, 2026 at 11:42:57 UTC (4:42:57 a.m. Pacific). The newest sampled order without it was **#408015**, also an Online Store order. This is a sharp platform/app rollout signature, not a property retained from an old Alabama test.

Across the complete sample:

- 743 of 1,000 orders contained `__ref_id`;
- all five inspected examples were `sourceName: web` and attributed by Shopify to the **Online Store** app;
- the attribute appeared on ordinary personalized hats, metal plates, and the CityLocs pack builder;
- nearly all sampled payments used Shopify Payments, with no useful gateway separation.

### Alabama comparison

Fourteen Alabama-related orders appeared in the 1,000-order window:

- twelve orders after the rollout contained `__ref_id`;
- two orders immediately before the rollout—#407151 and #407168—did not;
- the affected product handles included both `hat-alabama-plate` and `alabama-blackout-plate-hat`;
- Alabama line items carried ordinary `Custom Text` / `Custom Text Two` properties and no `__ref_id` line property.

Alabama therefore follows the same time-based rollout as the rest of the catalog.

## Source attribution

### Ruled out

The following were searched directly for both `_ref_id` and `__ref_id`, and their cart/order write paths were reviewed:

1. CityLocs live theme and pack-builder code.
2. The fixed-bundle Cart Transform and its allowlisted component properties.
3. The CityLocs post-purchase app, which removes underscore-prefixed properties when sanitizing carried line-item properties.
4. Zepto Product Personalizer's Alabama canvas script and shared storefront script. Zepto writes its own `_pplr_*` and `_pc_*` line properties, not `__ref_id`.
5. Product Warnings. It writes the explicitly named order attributes `Product Warnings` and `Checkout Alerts`, not `__ref_id`.
6. GemX. Its current global script writes a cart attribute named `gxId` when a campaign requires one, not `__ref_id`.
7. Shopify's public standard cart-action script and the visible global theme scripts.

### What remains possible

The exact owner cannot be established from the order record alone. Shopify exposes the order's source application but does not attribute each individual custom attribute to the code or app that wrote it.

An isolated headless-browser trace used a fresh profile and cart. It loaded the Alabama product, added a customized item, and navigated into checkout. The captured browser requests showed the expected `/cart/add.js` request but no client-side `/cart/update.js` or Storefront API mutation carrying `__ref_id`.

Combined with the sharp September 1 rollout and partial/progressive daily coverage, the strongest current inference is:

1. **Most likely:** a Shopify checkout/platform experiment, fraud/bot-defense mechanism, or server-side feature activated progressively for CityLocs.
2. **Also possible:** an installed app using a server-side checkout, pixel, or app-managed cart integration that is not represented by a public theme script.
3. **Unlikely:** CityLocs theme code or a product-specific personalization/bundle implementation.

Only Shopify or the owning app can definitively decode the value. A Shopify Plus support case should include the first observed order and exact onset timestamp and ask which platform/app subsystem owns private cart attribute `__ref_id`.

### Bot-incident correlation

CityLocs did have a documented catalog-scraper incident in August 2026. Claude's retained project notes and the incident brief show that the only storefront mitigation implemented by the CityLocs team was a custom `templates/robots.txt.liquid`: it preserved Shopify's defaults, disallowed a list of named crawlers, and added `Crawl-delay: 10`. It was deployed around August 10–13 and explicitly described as effective only for polite crawlers.

That theme change cannot create `__ref_id`: `robots.txt` is a static crawler instruction, does not run in a customer's cart or checkout, and contains no attribute-writing code. The team also drafted a Shopify Plus escalation requesting edge-level WAF, bot-management, managed-challenge, or rate-limiting assistance. The local records do not confirm which, if any, server-side control Shopify later enabled.

The timing makes a Shopify response to that escalation a credible lead: `__ref_id` began appearing progressively on September 1, after the August bot incident, and its shape and private checkout visibility are consistent with opaque server-side request correlation. This is a correlation, not proof. Shopify Plus Support must confirm whether `__ref_id` belongs to a bot-defense, fraud, checkout, or experimentation subsystem activated for the store.

## Automation risk assessment

### Value structure

All 743 sampled values were exactly 28 characters and every value contained at least one character outside `[A-Za-z0-9_-]`.

| Character class | Values containing it | Share of 743 |
|---|---:|---:|
| Percent sign `%` | 242 | 32.6% |
| Equals sign `=` | 209 | 28.1% |
| Ampersand `&` | 207 | 27.9% |
| Backslash `\` | 199 | 26.8% |
| Comma `,` | 186 | 25.0% |
| Question mark `?` | 154 | 20.7% |
| Whitespace | 147 | 19.8% |
| Double quote `"` | 135 | 18.2% |
| Slash `/` | 133 | 17.9% |
| Single quote `'` | 132 | 17.8% |

This is the main technical risk. A downloader that correctly parses Shopify's JSON response and ignores unknown order attributes will be unaffected. A downloader that concatenates unescaped attribute values into CSV rows, URLs, query strings, SQL, shell commands, filenames, or handcrafted JSON can fail only for certain random values.

That failure mode would be intermittent and could be mistaken for a product-specific problem. For example:

- an unescaped comma or quote can corrupt a CSV record;
- `&`, `=`, `%`, `?`, or `/` can corrupt an unencoded URL/query parameter;
- quotes and backslashes can invalidate handcrafted JSON or SQL;
- whitespace or shell metacharacters can break an unsafe command invocation.

### Recommended importer behavior

The production downloader should:

1. Treat Shopify order `customAttributes` / REST `note_attributes` as an array of arbitrary key-value metadata.
2. Ignore unknown keys by default; production routing should depend only on an explicit allowlist of required fields.
3. Explicitly drop `__ref_id` before flattening or exporting if it is not needed.
4. Use a JSON parser, a real CSV writer, parameterized SQL, and URL encoding rather than string concatenation.
5. Add a regression fixture containing a hostile but valid value such as `a,"b\\c&d=e%f?g/h'i j{k}`.
6. Log skipped orders with order number, stage, and sanitized error reason rather than silently omitting them.

Dropping `__ref_id` at ingestion is safe for CityLocs production routing because none of the reviewed CityLocs code consumes it. Do not remove it from Shopify orders until its owner is confirmed; simply ignore it in the production downloader.

## Immediate diagnostic plan

1. Obtain two or more order numbers that failed to download and two successful neighboring orders.
2. Compare their raw API responses and importer logs, particularly the exact `__ref_id` values and escaping characters.
3. Run the production importer against saved, sanitized fixtures with and without `__ref_id`.
4. If removing only `__ref_id` makes a failed fixture import successfully, fix the parser rather than modifying checkout behavior.
5. Separately verify Alabama's product/variant mapping because a routing defect can coexist with the new private attribute. The current evidence does not support `__ref_id` as an Alabama-only cause.
